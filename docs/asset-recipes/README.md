# Asset Recipes

Creates and wires a whole set of related assets from a recipe held as editable data.

Unreal Engine **5.8**, Windows. Editor-only. No content, no runtime cost, nothing to shut off in a
shipping build.

---

## The problem

Every new content item — a weapon, an enemy, a pickup, a UI screen — means making the same six to
ten assets by hand and connecting them:

- the Blueprint, from the right parent class
- the Material Instance, from the right master material
- the DataAsset that holds the tuning values
- the DataTable row that registers it
- the folders, all named to the studio convention

It is done weekly. It is done slightly differently every time. Juniors get it wrong, and nobody
notices until something does not show up in a menu. Studios eventually write an Editor Utility
Widget to do it, and that widget becomes a small unowned codebase that rots.

## What this does

A **recipe** is a JSON file. It names the steps, the naming and folder patterns, and which property
on one asset points at another. You run it with an item name:

```
UnrealEditor-Cmd.exe <YourProject>.uproject -run=AssetRecipes ^
  -Recipe="Recipes/Weapon.json" -Name=Sword
```

That is a **preview**. It writes a proof sheet and touches nothing. Add `-Apply` to perform it.

### Recipes are text, and that is the point

A recipe is a studio convention, and a convention has to survive code review. A DataAsset is a
binary `.uasset`: two leads editing one produces a merge conflict no version control can resolve,
and a reviewer sees "binary file changed". A JSON recipe diffs line by line, reviews in a pull
request, greps, and can be generated by a build script.

## A recipe

```json
{
  "recipe": "Weapon",
  "version": 1,
  "tokens": { "Category": "Weapons" },
  "steps": [
    {
      "id": "material",
      "kind": "create",
      "class": "/Script/Engine.MaterialInstanceConstant",
      "path": "/Game/{Category}/{Name}/Materials",
      "name": "MI_{Name}",
      "factory": { "InitialParent": "/Game/Art/Materials/M_WeaponMaster.M_WeaponMaster" }
    },
    {
      "id": "blueprint",
      "kind": "create",
      "class": "/Script/Engine.Blueprint",
      "path": "/Game/{Category}/{Name}",
      "name": "BP_{Name}",
      "factory": { "ParentClass": "/Game/Core/BP_WeaponBase.BP_WeaponBase_C" },
      "set": { "SkinMaterial": "@material" }
    },
    {
      "id": "row",
      "kind": "row",
      "table": "/Game/Data/DT_Weapons.DT_Weapons",
      "row": "{Name}",
      "set": { "DisplayName": "{Name}", "Actor": "@blueprint" }
    }
  ]
}
```

Three example recipes ship in the plugin's `ExampleRecipes` folder. Copy one and edit the paths to
match your project.

### Step kinds

| kind | what it does | needs |
| --- | --- | --- |
| `create` | makes a new asset through the engine's own factory for that class | `class`, `path`, `name` |
| `duplicate` | copies an existing template asset | `template`, `path`, `name` |
| `row` | adds or replaces one row in an existing DataTable | `table`, `row` |

`duplicate` covers every asset type, including ones with no factory at all — Behaviour Trees, Widget
Blueprints, Niagara systems. Most studios already keep template assets; this points at them.

### Tokens

`{Name}` is the item name you passed. `{Recipe}` is the recipe's name. Anything in `tokens` is
available too, and `-Set=Key=Value` on the command line overrides it for one run.

**An unknown token stops the run.** It does not pass through. `BP_{Nmae}` would otherwise create an
asset literally called `BP_{Nmae}`, in a folder named after the same typo.

### Wiring

`"set"` assigns properties once every asset in the run exists. A value starting with `@` refers to
another step by id and resolves to the asset that step produced.

Because wiring happens after everything is created, **step order does not matter**. A step may refer
to one declared later, and two steps may refer to each other.

Values are written as strings and read through the engine's own property text format, so object
references, numbers, enums, names and structs all work without any special syntax.

## Running it again is safe

Re-running a recipe for the same item name is **idempotent**: assets that already exist are left
exactly as they are, and their wiring is re-applied.

That is what makes a recipe editable. Add a step to `Weapon.json` six months in, re-run it across
every weapon you have, and the new asset is created for each one while nothing existing is
disturbed.

## It refuses rather than half-finishing

The whole run stops, before anything is written, on:

- an unknown token or an unclosed `{`
- a `@reference` to a step that does not exist, or to itself
- two steps that would write the same asset
- a `row` step whose DataTable is not there
- a duplicate step id, an unknown `kind`, or a missing required field

A half-populated project is worse than an unpopulated one, so none of these is a warning.

## The proof sheet

Every run writes a self-contained HTML sheet — every asset it would create, every one that already
exists, every property it would wire and what it points at. It opens offline, out of a zip, forever.

Default location: `Saved/AssetRecipes/AssetRecipes.html`. Override with `-Report=<file.html>`.

## Batches

```
  -Name=Sword                     one item
  -Names=Sword,Axe,Bow            several
  -NamesFile=weapons.txt          one name per line, # starts a comment
```

## Command line

```
  -Recipe=<file.json>   the recipe to run. Required.
  -Name=<Item>          the item to make, available to patterns as {Name}.
  -Names=<a,b,c>        several items in one run.
  -NamesFile=<file.txt> one item name per line.
  -Set=<Key>=<Value>    override or add a token. Repeatable.
  -Apply                perform the plan. Without it, nothing is written.
  -Report=<file.html>   where to write the proof sheet.
```

## Exit codes

| code | meaning |
| --- | --- |
| 0 | everything asked for succeeded |
| 1 | the command line was wrong |
| 2 | the recipe could not be read or parsed |
| 3 | the recipe parsed and the plan was refused |
| 4 | the plan was fine and a write failed |

Distinct values so a build server can tell a broken recipe from a broken project. A single non-zero
would make it useless in CI.

## Revision control

When revision control is configured, every file the run is about to write is checked out first, and
the proof sheet says so. Assets that already exist and gain no new wiring are **not** checked out —
a tool that re-saves files it did not change turns a two-file change into a twenty-file changelist.

## Installation

1. Copy the `AssetRecipes` folder into your project's `Plugins` folder.
2. Restart the editor. Enable **Asset Recipes** under Edit → Plugins → Editor if it is not already on.
3. Copy a recipe out of `ExampleRecipes` and edit the paths.

## What it does not do

Stated plainly, because a tool's limits should be findable before purchase rather than after.

- **It does not create DataTables.** A `row` step writes into a table you already have. Creating one
  would mean choosing a row struct on your behalf.
- **It does not edit Blueprint graphs.** It sets Blueprint *defaults* — the values on the class
  default object. Nodes and wiring inside the graph are untouched.
- **It does not undo a run.** Every run is a preview first, which is the safety mechanism; assets it
  creates are ordinary assets and are deleted the ordinary way.
- **Verified on Unreal 5.8 only**, because that is the only engine it has been built and run
  against. It is not claimed to work on 5.3.

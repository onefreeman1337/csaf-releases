Your effect disappears when the camera pans away from it. Not faded, gone, in a single frame, while particles are still visibly on screen. It looked fine in the editor and it looks wrong in the packaged build.

That is bounds culling. A Niagara system on dynamic bounds is culled by its own bounding box, and once the box leaves the frustum the whole system stops drawing.

The engine gives you two tools for this and neither one solves it

  • A validator that checks presence, not correctness. It tells you a system has no fixed bounds. A system whose bounds are set but wrong, typed in by hand or captured from a frame where the effect had barely started, passes clean. That is the case that actually ships.
  • A per-asset button that samples one frame. Set Fixed Bounds uses whatever is on screen the instant you press it. For anything that moves, expands or arcs, one frame is not the shape of the effect. Press it before the first particle spawns, or after a burst has died, and it does nothing at all, without saying so.

There is no batch path in the engine, and there is a structural reason: computing a correct bound requires simulating the system, and validation is static.

So this simulates them

For every Niagara system in your project, Niagara Bounds Solver plays it headlessly one tick at a time and takes the union of its local bounds across every tick in which a particle was actually alive. That union, the effect at its widest rather than at one arbitrary instant, is written as FixedBounds.

Every run writes an HTML sheet drawing the box your asset carried against the box it measured, to a shared scale, so "this one was 210,590 times too small" is something you can see rather than something you are told.

Getting Started

Three steps, and the first one writes nothing.

  1. Install. Copy the NiagaraBoundsSolver folder into your project's Plugins folder and reopen the project. Accept the rebuild prompt if it appears. Confirm it loaded under Edit > Plugins > Editor, where it is listed as Niagara Bounds Solver.
  2. Preview, from the editor console. Press the backtick key to open the console and type NiagaraBounds.Solve then Enter. Nothing is written. The log prints the path of an HTML report under YourProject/Saved/NiagaraBoundsSolver/; open it and read the per-system table.
  3. Apply, once you are happy with the report. Type NiagaraBounds.Solve -Apply. An undo journal is flushed to disk in full before the first asset is modified, so NiagaraBounds.Solve -Revert puts everything back even if the run dies part way through.

Headless, for a build step:

UnrealEditor-Cmd.exe "D:/Projects/YourProject.uproject" -unattended -nosplash -ExecCmds="NiagaraBounds.Solve -Apply -ExitOnFinish"

Or as a commandlet: -run=NiagaraBoundsSolver -Path=/Game/Effects -Apply. Exit codes are meaningful and an empty scan is a failure, not a pass, because a CI step that returns zero because it looked at nothing is a step that can never fail.

The rule it will not break

A system it cannot honestly simulate is reported as skipped and left exactly as it was. No particle alive at any sampled tick. Still running at the time cap, such as a looping system. An instance that will not start. A GPU system in a run with no rendering device. A system using a stateless (Lightweight) emitter, added in UE 5.5, which this version does not measure and names as stateless-emitter-unsupported rather than writing a default. Mixed systems are refused too, because a union covering only the standard emitters would be an under-bound, which is the very bug this removes.

A wrong bound is worse than an absent one, because an absent one is at least flagged by the engine's own validator and a wrong one validates clean and ships.

What it changes, precisely

On each solved system: bFixedBounds and FixedBounds. On each GPU emitter still on dynamic bounds: CalculateBoundsMode and its FixedBounds, because the engine does not support dynamic bounds on GPU emitters. CPU emitters on dynamic are deliberately left alone. Nothing else is touched: no module, parameter, renderer, script, spawn rate, material or scalability setting.

Technical Information

Features:

  • Measures Niagara bounds by simulating each system tick by tick and taking the union across its whole lifetime, rather than sampling one frame
  • Batch writes FixedBounds and CalculateBoundsMode across the whole project in one pass, with an optional percentage pad
  • Designed HTML report per run: old box against measured box drawn to a shared scale, plus ticks simulated, ticks containing particles, and the volume change
  • Undo journal flushed to disk before the first write, with -Revert to restore
  • Refuses and names any system it cannot honestly measure instead of inventing a bound
  • Editor console command and commandlet sharing one code path, with meaningful CI exit codes
  • Automation tests covering the union accumulator and argument handling, including tests that pin the engine behaviours the product relies on

Code Modules:

  • NiagaraBoundsSolver (Editor)

Number of Blueprints: 0

Number of C++ Classes: 10

Network Replicated: No (editor-time asset tool; nothing runs at game time)

Supported Development Platforms: Windows

Supported Target Build Platforms: Win64

Documentation: https://github.com/onefreeman1337/csaf-releases/blob/main/docs/niagara-bounds-solver/README.md

Example Project: None. The plugin operates on the Niagara systems already in your own project and ships with no content, so a sample project would demonstrate nothing the three Getting Started steps above do not. The full C++ source is included.

Honest about its limits

A simulation is not a proof. Systems are played in isolation, so an effect driven by gameplay parameters or by data interfaces that read the scene around it may occupy more space in your game than it does alone in an empty world. Randomness is sampled once, not bounded. The report states how many ticks were simulated and how many contained particles, so the basis of every number is visible, and the pad is there for the variance you expect.
